Web Design System, Aura

Two teams, no shared language, and a design file that had stopped matching the site.

Company

Workhuman

Year

2024 – Ongoing

Role

Designer, Design Systems

Team

Web

Context

Workhuman’s website is built by two stateside teams: web designers working in Figma, and web developers working in Storybook and Contentful. Over time the two had drifted apart; spacing didn’t match, type scales didn’t match, and none of it was documented. An audit turned up more than fifteen button implementations alone.

The Ireland product design team owns Workhuman’s product design system. Their goals are different from ours, so the web system was never meant to copy theirs. Where the two overlap in Figma, we brought them in so the web system would follow the same practices.

3

designers on the systems team

4

15

designers + engineers consuming it

Problem

Every handoff between design and development started from a different place. Designers drew one thing, developers built another, and both sides lost time asking the same questions.

“We spend 60% of our time asking the same design questions.”

Engineering, discovery interviews

So the first job wasn’t new components but rather a shared layer both teams could trust: named decisions about color, spacing and type that move between Figma and code without being reinterpreted at every handoff.

Solution

Establishing a shared source of truth

I set up a four-tier token model: primitives, aliases, semantic tokens and component tokens. Each tier exists so a decision gets made once and lands the same way in Figma, in code, and in the conversation between the two teams.

Aura V3 later collapsed this to three tiers (primitives, aliases and component tokens), mirrored one-to-one with code.

Making the token chain visible

Take the white button’s focus state. The focus ring uses border/acc-default, which points to humanity/60, which is the primitive #5B63E4. One annotated component showing the whole chain did more for adoption than the documentation site did.

DECISION FORK

Name tokens the way designers think, or the way developers think?

Designers name things by how they look and by contrast, developers name them by where they’re used. Naming tokens after how they looked in Figma was the easy route, and it broke the first time the Brand team shifted a hue: humanity/60 was still called humanity/60 and no longer described anything. On the second pass we named tokens by role, so a value can change without the name going stale. The tradeoff is that designers can’t guess a token from how it looks anymore, so the documentation matters as much as the library.

Governing contribution, instead of policing it

Anyone can add to the system through a six-step process: request, show three or more use cases, design review, engineering check, docs, ship. Every release gets a version number and a changelog. Deprecations get six months’ notice and a migration guide.

Impact

Over the rollout, the system went from a source of friction to where both teams start.

Fifteen-plus button implementations became one component. New designers got productive in days instead of weeks, by the team’s own estimate.

150+ components · 200+ icons · 8pt grid · 6-size type scale · WCAG AA compliant

V3

By 2026 the design file had drifted from the site again: the wrong typeface in Figma, layout specs that no longer matched the code, and themes the CMS used every day that weren’t drawn anywhere.

For V3, my web developer partner and I redid the original work with Claude Code, connected to Figma through MCP: the audit, the rebuild, and the connection to Storybook and Contentful. I did the audit and the design rebuild. Cam O. connected it to the codebase, Storybook and GitHub. What took months the first time took two weeks this time.

We’re now looking at the same workflow for future brand and site updates, not just audits.

Learning

A design system’s users are designers and developers, and they act like any other users: they go around anything slower than what they already do. Aura got adopted once grabbing a component was faster than rebuilding one. Most of the work was removing reasons to go around it.
